<Definition term={"Prompt Engineering"}>
Prompt engineering is the design of instructions, examples, constraints, schemas and interaction patterns that steer a model toward useful, testable behaviour for a specific task. In production it is not just wording: it includes prompt versioning, input validation, structured outputs, retrieval context, refusal boundaries, regression tests and measurement of failure cases.
</Definition>

## Why It Matters

Prompt engineering designs instructions and examples that elicit useful model behaviour. It includes task definition, constraints, output schemas, examples and explicit uncertainty handling.

A prompt is only one part of the context. Treat it as an interface contract for a model call, then verify the resulting behaviour with representative examples rather than relying on phrasing alone.

<EngineeringMode>
In engineering terms, prompts are part of the application contract. Architecture must decide where prompts live, how versions are deployed and what context may enter them. Design must specify tone, refusal boundaries and output shape. Build work includes schemas, fixtures and regression tests. Operations monitor drift, cost and failure clusters. The recurring risk is treating phrasing as magic instead of maintaining it like code.
</EngineeringMode>

<RealExample>
Khan Academy’s Khanmigo-style tutoring scenario shows prompt engineering beyond wording. The system prompt must guide the tutor to ask questions, avoid simply giving answers, respect student safety boundaries and produce age-appropriate explanations. Good prompts become testable instructional policy, not just clever phrasing.
</RealExample>
