<Definition term={"Data Modelling and Data Engineering"}>
Data modelling defines the entities, relationships, events, identifiers, semantics and lifecycle states that software relies on. Data engineering builds the pipelines, storage, validation, lineage and access patterns that make data usable. AI systems need both: models can only reason well over data that is coherent, current, governed and connected to the business meaning of the task.
</Definition>

## Why It Matters

Data modelling represents entities, relations, events, constraints, lineage and lifecycle. AI does not compensate for ambiguous semantics or poor-quality source data.

For AI applications, data engineering also includes provenance, freshness, retention and access policies for retrieved context, traces, feedback and eval datasets.

<EngineeringMode>
Data engineering defines the raw material of AI behavior. Architecture must handle lineage, consent, permissions, freshness, schemas and retrieval indexes. Design must account for missing or uncertain data in the user experience. Build work includes validation, migration and backfill paths. Operations monitor data drift and quality incidents. The risk is blaming the model for failures caused by broken or poorly governed data.
</EngineeringMode>

<RealExample>
A product-search assistant is only as good as its data pipeline. Catalog records need consistent names, prices, availability, variants, permissions and embeddings. If discontinued items or restricted products leak into the index, the language model may confidently recommend something users cannot buy.
</RealExample>
