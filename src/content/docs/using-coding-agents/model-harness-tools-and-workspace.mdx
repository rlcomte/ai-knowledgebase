<Definition term={"Model, Harness, Tools and Workspace"}>
A coding agent's capability is the product of four layers: the model that reasons and generates text, the harness that manages state and execution, the tools that expose concrete actions, and the workspace that supplies files, environment, credentials and repository history. Changing any layer can change the agent's behaviour, risk profile and evidence quality even when the user prompt stays the same.
</Definition>

## Why It Matters

The model supplies language understanding, code generation and reasoning. Model capability matters, but does not determine the agent's complete behaviour.

The harness provides tool execution, file access, state, context assembly, approvals, sandboxing, progress, retries and stopping conditions. Different harnesses can produce substantially different outcomes with similar models.

Tools are controlled capabilities such as repository search, file editing, shell execution, browser access, issue tracking or deployment. The workspace model is the files, repository state, environment and connected resources visible to the agent.

<EngineeringMode>
This concept defines the real system boundary for coding agents. Architecture includes the model, harness, filesystem, shell, permissions and connected services. Design should make state and authority visible. Build work configures tools, instructions and verification commands. Operations audit actions and failures. The risk is attributing results only to the model while ignoring the harness that enabled or constrained the work.
</EngineeringMode>

<RealExample>
Codex illustrates the distinction between model and harness. The model reasons about the request, while the harness provides repository files, patch application, shell commands, approval prompts and workspace state. Most engineering value comes from combining language reasoning with controlled access to real project artifacts.
</RealExample>
