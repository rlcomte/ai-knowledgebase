<Definition term={"Configuration, Permissions and Sandboxing"}>
Configuration controls model choice, reasoning effort, tool availability, external integrations and runtime behaviour. Permissions define which reads, writes, commands, network calls or external actions require approval. Sandboxing constrains the file system, process and network environment in which the agent operates. These controls reduce blast radius but must be paired with secret management, audit logs and human review.
</Definition>

## Why It Matters

Model and reasoning configuration should match task complexity, latency and cost. Easy, bounded edits may not need the most expensive setting.

A sandbox is an execution boundary that restricts file, process or network access. It reduces blast radius but does not replace secure review. Approval policy governs which actions require human consent; high-impact, external, destructive or credential-sensitive actions deserve tighter approval.

MCP integrations expose external tools and resources. Each integration still needs scoped credentials, clear tool contracts and safe defaults. Secrets should come from managed mechanisms, not prompts or committed files.

<EngineeringMode>
Configuration and sandboxing define the agent's operating envelope. Architecture must separate read, edit, network and destructive capabilities. Design should make approval prompts understandable and timely. Build work encodes allowed tools, blocked paths and project instructions. Operations review logs and tighten defaults after incidents. The risk is granting broad authority to an agent whose plan, context or commands have not been verified.
</EngineeringMode>
